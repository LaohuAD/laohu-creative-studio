# 基础架构与回归验收

检查日期：2026-09-12。范围：现有无限画布的本地启动、网络提交、数据保存、更新交付、测试与扩展边界。影院暂不实施，其需求见 [影院功能需求](影院功能需求.md)。

当前运行环境规则（2026-10-06）：项目统一使用 Python 3.14.5，根目录 `.python-version` 为唯一版本真源；Mac/Windows 回归与 R2 发布工作流均读取该文件。Windows 仓库内 `python/` 使用完整官方发行包，CI 通过该解释器创建标准 venv、离线安装 `packages/`、执行 `pip check` 和核心依赖导入。跨平台主机上的 `pip --platform` 解析不能证明目标平台条件依赖完整；Windows wheelhouse 必须在 Windows 项目内置 Python 的真实 venv 中离线安装并通过 `pip check`。R2 更新包包含 `.python-version` 以便旧安装获得新环境要求，但不包含整套 `python/` 运行时；更新器负责下载、准备并验证运行环境。下文 2026-09-12 的 3.10/3.14 矩阵、部分 wheelhouse 和“不升级解释器”描述是当时的历史验收记录，不代表当前版本规则。

## 把建议说清楚

| 建议 | 在这个产品里具体指什么 | 判断 |
|---|---|---|
| 网络底层框架选好 | 浏览器如何联系本地服务，本地服务如何提交云端任务，断网/超时如何恢复 | 现有 FastAPI、Uvicorn、HTTPX 可以继续用；本次发现的问题主要是重试和生命周期策略，不足以证明必须换框架。 |
| 固定测试几个模板 | 保留稳定的创作案例，每次修改重跑，核对输入、参数、引用与结果 | 模板应该覆盖正常、失败、取消、恢复、导入和升级，不能只验证几张图能生成。 |
| 上版功能和 bug 下版再验证 | 新功能加入后，旧功能仍需通过；修过的 bug 留下防复发用例 | 已有大量测试，但此前 R2 发布只跑发布脚本测试，没有 Mac/Windows 全套检查门槛。 |
| 模块化 | 同一职责有一个清楚的归属，页面通过稳定接口协作 | 存储、能力档案、Agent 和部分共享界面已有模块；主后端约 2.2 万行、主画布 JS 约 2.8 万行，继续往里堆功能会增加连带修改风险。 |
| 先底层和交互 | 先稳定数据、执行、失败处理及共享控件，再加业务页面 | 新影院应复用素材、运行和参数组件，不能再造第二套生成系统。 |

这里的“模板”是回归场景，不是创作提示词模板；“回归”就是确认新改动没有把以前能用的东西改坏。Mac 和 Windows 是系统差异，Python/依赖版本是运行环境差异，数据格式版本是兼容差异，需要分别验证。

## 现有基线和可复用能力

- `project_storage.py` 已有数据/素材/结果分层、SHA-256 去重、稳定引用、同进程锁和临时文件写入后原子替换。
- 模型能力档案与用户启用列表分开，当前节点可共用参数语义与运行前预检。
- Agent 命令有稳定请求 ID、持久化和去重逻辑；目前执行仍依赖打开的画布。
- 媒体预览、数值控制、参数面板和部分导演台逻辑已经独立或共享；应继续从这些组件扩展。
- 原有测试不仅有代码结构检查，也包含 Node 执行、临时素材、HTTP 模拟平台和 ZIP 往返。代码结构断言不能替代真实浏览器或操作系统验收。

## 方案比较与本轮选择

| 方案 | 保留与变化 | 数据/学习成本 | 风险与验收 |
|---|---|---|---|
| 保守修补 | 保留所有组织结构，只修具体 bug | 最低 | 很快，但新功能容易继续增加耦合；仍须全量回归。 |
| 按职责逐步抽离（本轮选择） | 保留框架、现有数据和界面，把共同启动/重启/安装移入同一模块，固定测试与发布门槛 | 无需用户迁移现有作品 | 小范围行为变化可单独验证；后续每次抽离一个业务边界，保留接口与数据含义。 |
| 完全替换框架 | 重写网络、数据和页面 | 最高 | 现有功能、历史画布与跨平台行为都需重新验证，当前没有足够收益支持这项投入。 |

不以“大文件拆成很多小文件”作为验收目标。真正的目标是修改模型参数不需要修改素材保存，新增影院页面不需要复制网络生成、默认设置、引用与任务逻辑。

## 本轮改动与证据

| 问题 | 改动 | 验证 |
|---|---|---|
| Mac 双击启动按端口强杀进程，可能中断其他程序和正在生成的任务 | `local_runtime.py` 识别现有画布并复用；其他程序占用端口时说明原因，不结束它 | 本机启动脚本真实连接现有画布；模拟其他服务占用，无进程创建或停止 |
| 安装与运行选用不同 Python；失败也可能显示完成 | Mac 使用项目 `.venv`；Windows 优先现有便携 Python，否则项目 `.venv`；安装和运行共用选择逻辑；保留真实退出码 | 环境选择、失败返回测试；检查两端脚本 |
| 固定等 3 秒就打开浏览器 | 检查 `/api/app-info` 确认真正就绪，失败不打开空白页 | 随机端口真实子服务启动/退出测试 |
| 自更新重启使用过时文件名、拼接 Shell 和强杀 PID | 运行中的服务通过独立请求文件通知启动器，由启动器重启自己创建的进程；直接 `python main.py` 启动的服务需要手动重启 | 随机端口真实子服务完成请求重启→第二次启动→正常结束，浏览器只开一次 |
| 付费 POST 遇到 503 或读超时可能被自动重复提交 | 通用重试函数只自动重试 GET/HEAD/OPTIONS；提交保留原失败，不能以重发代替查询 | 测试先复现 3 次 POST，修复后只提交 1 次；GET 仍能重试恢复 |
| Windows 设备名、中文长文件名跨平台失败 | 对新文件统一规范设备名、字节长度，保留扩展名并为截短名称加稳定摘要 | 设备名、常规中文名、长中文名测试；不批量重命名用户旧文件 |
| 损坏索引或未来版本索引可能被当成空库后写回 | 索引解析、结构或版本异常时阻止写入，保留原文件；提示检查磁盘、恢复备份或使用新版 | 损坏 JSON、错误列表、未来版本分别验证写入被拒绝且原内容未变 |
| R2 更新遗漏 Agent 文档和 CLI | 运行说明放在 `static/agent-guide.md`，CLI 放在根目录 `canvas_cli.py`，沿用旧更新器已接受的目录，不放宽白名单 | 发布白名单与私有路径排除测试 |
| 依赖随安装日期漂移 | 固定当前验证过的直接依赖；Python 3.10 使用兼容的 websockets 分支 | 本机依赖检查；CI 负责 3.10 和 3.14。尚未建立完整间接依赖哈希锁，不宣称完全可重复安装 |
| 新版发布缺少双平台全量回归门槛 | 统一 `tools/check_regression.py`；GitHub Actions 配置 Mac/Windows × Python 3.10/3.14；R2 发布依赖矩阵成功 | 本机跑全套；远端矩阵须提交推送后才运行，配置存在不等于 Windows 已实测 |

启动器默认打开 `http://127.0.0.1:3000/`，便于本机访问和剪贴板等浏览器能力；服务原有局域网监听保持可用。用户从局域网地址进入时，Agent 说明仍按实际页面地址生成，不硬编码回环地址。启动器不会修改现有画布默认参数、API Key 或模型启用列表。

依赖安装的临时文件和 pip 缓存置于项目 `cache/runtime/`。现有 `packages/` 是部分平台/版本的离线包，不能承诺任意系统离线安装；不匹配时明确转在线安装。本轮没有重装用户运行环境，也没有触发付费生成。

## 每个版本必须重跑的固定场景

| 场景 | 正常路径 | 必测异常/旧 bug |
|---|---|---|
| 启动和更新 | 安装→启动→页面就绪→二次启动→更新重启 | 端口占用、缺依赖、路径含中文/空格、失败退出、同服务复用 |
| 素材与保存 | 文本/图片/视频/音频上传→引用→改名→重开 | 同内容去重、Windows 名称、文件丢失、索引损坏、未来格式禁止覆盖 |
| 五类生成 | 文本、图片、视频、音频、音乐分别输入→选参数→预检→结果 | 参数不支持、缺输入、任务超时、不重复付费提交、语音与音乐不串路由 |
| 并行任务与结果版本 | 同一执行节点连续提交→独立结果→重开恢复 | 失败有原因、取消不误报失败、旧结果不丢、重复回写去重 |
| Agent 与手动创建 | Agent 读默认→创建/填充/连接/运行；手动继承同类最近设置 | request_id 去重、显式参数覆盖、默认互不混用、页面关闭后不虚报已执行 |
| 导出导入 | 画布和资源 ZIP→新画布导入→文件和引用重映射 | 缺资源明确失败、同名不同内容、中文名称、旧包兼容、原作品不被覆盖 |
| 交互统一 | 下拉、数字输入、滑块、排序、预览、快捷键在不同节点一致 | 弹层遮挡/截断、编辑焦点丢失、复制媒体与复制节点混淆、中英文不同步 |
| 升级与恢复 | 更新包→程序和能力档案→原数据重开→需要时回滚 | Agent 运行文件遗漏、版本显示不一致、私有文件不得打包、不能静默清空索引 |

本机自动检查：在项目目录执行 `.venv/bin/python tools/check_regression.py`（Windows 使用 `.venv\Scripts\python.exe`，便携版使用 `python\python.exe`）。Node.js 22+ 是开发回归所需工具，不是用户正常启动画布的额外前提。

自动测试通过后仍须真实浏览器检查本轮改动入口。涉及 Windows 剪贴板、文件选择、FFmpeg、CLI、启动和更新的版本，还需 Windows 实机冒烟检查。模板使用临时媒体和模拟平台，不自动调用用户的付费模型。

## 尚未完成、后续扩展必须遵守的边界

1. 主后端与主画布 JS 仍偏大。新增影院时应单独组织作品数据和接口；后续触及现有生成业务时再按任务执行、素材接口、参数控件逐项抽离，不能把影院直接塞进两个主文件。
2. 当前 JSON 文件锁是同进程锁，不是多进程事务。不能仅把 Uvicorn workers 改大就当作支持多人并发；如需多进程/多用户，要先设计数据库事务和跨进程任务协调。
3. 本次索引保护不等于所有历史 JSON 读取路径都已重构。配置、历史导入和画布迁移仍需遵守各自版本与备份规则，后续逐项验证，不能一律用空对象吞掉错误。
4. 当前定位仍是本机/可信局域网工具。HTTP 与 WebSocket 已共用 Host/Origin 校验，拒绝外来网站跨源操控；这不等于多用户鉴权。若转公网托管，仍需身份、作品权限和密钥隔离，不能直接映射本地端口上线。
5. 本轮没有在原生 Windows 或 Intel Mac 上运行桌面交互，也未验证远端平台实费调用；CI 通过也不能替代这些场景的实机检查。

## 未发布阶段内核重构（2026-09-12 补充）

用户已明确：当前功能、数据与结果是保留对象，旧架构和旧更新器本身不必兼容。此要求取代上文以旧更新器目录限制新模块的考虑。

**目标：** 让共享基础能力可独立维护和测试，并证明一处失败不会无界影响其他请求、页面或文件。

**架构选择：** 采用模块化的单个本地服务。相比原样修补，它提供明确职责边界；相比拆成多个后台服务，它保留一次启动、同盘数据和较低安装维护成本。采用 `canvas_core/` 承载稳定运行组件，业务通过显式接口接入，不向新模块注入整个 `main` 或全局字典。

**技术：** 保留当前已验证的 Python/FastAPI/HTTPX 和浏览器界面。模块化不依赖更换框架。先做内部替换和故障测试，后做全量回归与实际 HTTP/WebSocket 验证。

执行顺序与验收：

- [x] 实时消息：迁出 `ConnectionManager` 到 `canvas_core/realtime.py`；每个连接独立发送锁和超时，并行广播，清理失败连接及其索引。模拟卡住、抛错和重连，确认正常连接及时收到原格式消息。
- [x] 网络策略：重试逻辑归入 `canvas_core/transport.py`；业务只通过明确请求方法调用。保持只读重试、提交不重发、取消向上传递，测试实际 HTTPX 请求次数和状态。
- [x] 数据文件：`canvas_core/json_store.py` 统一原子写入及失败清理，接入素材索引、Agent 命令和画布保存；磁盘写入/替换失败时原文保留且不残留半写文件，不同画布互不串写。
- [x] 请求边界：`canvas_core/request_boundary.py` 统一浏览器请求来源检查；保留本机、当前局域网页面和无 Origin 的 CLI，拒绝其他网站跨源调用和不属于本机服务的 Host；验证 HTTP 和 WebSocket。
- [x] 发布与依赖边界：更新器允许正式 `canvas_core` 程序模块；增加本地模块依赖检查，模块缺失或反向导入 `main` 时检查失败，不依赖人工记住每个新增文件。
- [x] 运行完整回归和真实服务冒烟，更新本节状态与边界。此次不新增影院，不迁移或删除用户数据，不宣称完全消除故障或已经支持公网多用户。


### 本轮模块化结果

- `canvas_core/realtime.py`：连接索引、发送锁、有界超时、并行通知与坏连接清理；不依赖业务入口。
- `canvas_core/transport.py`：HTTP 请求恢复策略；不读取用户配置或创建全局网络客户端。
- `canvas_core/json_store.py`：统一读取与原子写入，只有文件不存在允许默认值，写入失败清理临时文件；画布、项目目录、素材索引和 Agent 命令接入共同实现。
- `canvas_core/request_boundary.py`：HTTP/WebSocket 来源边界和同源预检；不使用 DNS 查询决定每次请求是否可信，不对外宣称身份鉴权。
- `tools/check_regression.py`：检查模块缺失和核心反向导入，并运行完整回归；`tools/publish_r2.py` 复用模块检查，遗漏新文件时阻止打包。
- 画布列表、项目列表、回收站列表和画布/元数据读取移到后台线程，读取后迁移与保存使用锁保护。模拟慢磁盘验证事件循环仍能继续运行。

当前没有改变作品、素材、模型参数或生成结果格式，不需要数据搬迁或清库。原有入口函数只负责接入组件，测试验证实际结果，不再把原子写入必须留在 `main.py` 当作限制。模块化单服务仍共享一个进程，进程退出和物理磁盘故障不属于连接级隔离能够完全解决的问题。

最终验证：690 项测试通过，24 个前端脚本语法通过；真实本机页面、画布/项目列表和 Agent 文档返回成功，WebSocket 统计与心跳成功，外来 Origin 的 HTTP/WebSocket 均被拒绝。工作区模拟打包得到 113 个文件、约 3.2 MB，包含全部 5 个内核包文件；仅校验，未上传，生成的临时包已删除。Windows 尚未实机运行，已纳入原有自动测试矩阵。

共享基础内核已独立；主后端的模型适配、素材业务和前端节点业务仍存在较大文件。它们尚未全部完成领域拆分，不能把本轮结果称为全项目重写完成。后续新增影院使用独立业务模块，通过已稳定的素材、参数、任务和存储接口接入。

## 创作进度与任务边界（2026-09-12 补充）

本次继续采用模块化单服务，保留现有模型能力档案、参数校验、平台协议与生成结果。新增三个独立组件：

- `static/js/canvas-production.js`：登记分段与实际节点引用，校验原文切片，派生五列状态表；通过显式回调读取节点、聚焦画布和调用视频首帧组件。不会复制媒体，不另存完成状态，不解析自由 Markdown 猜资产。一次刷新复用节点索引、共用任务索引与原文字符数组，避免每个资产重复扫描整张画布。
- `static/js/canvas-model-client.js`：HTTP 单次提交、错误解析、取消信号传递与批量部分成功。图片通用提交、视频、音频和音乐 JSON 请求接入；不自动重试付费提交，不承担模型 Schema 或平台协议转换。
- `canvas_core/task_execution.py`：后台任务状态转换、存储同步、取消与异常收尾。图片和 ComfyUI 任务显式传入存储、任务容器、锁与执行回调；模块不反向导入 `main`，也不接受整份业务全局变量。

故障验证覆盖独立任务成功/失败互不改写、取消后执行器迟到仍不回写、提交前磁盘写入失败则不调用模型、等待状态保留上游编号。结果已产生但后续状态存储失败时，内存保留结果并报告同步错误，不能为了恢复界面重新计费提交。这些保证不能替代多进程事务或机器断电后的数据库恢复。

验证：完整回归 716 项通过；19 个前端主脚本语法及模块边界检查通过。Mac Chrome 实际验证 Agent 登记、自由说明、共享资产、刷新保留、视频首帧、音色占位、平滑导航、中英文和窄屏布局。Windows 未实机运行；本次新增模块使用跨平台 Python/浏览器 API，未更改 Windows 启动方式，平台矩阵仍需发布前实际运行。

仍待逐项抽离的业务：各平台专用请求适配器、文本流式响应、RunningHub 专用执行路径、前端大部分节点编排和素材业务。当前已建立可独立维护的调用与任务边界，但不是全项目领域拆分完成。后续扩展沿这些接口移动具体业务，不复制两套执行或状态逻辑。


## 安全升级收尾与后续计划（2026-09-13）

本轮优先完成升级，不继续扩大业务拆分范围。

已实现：`canvas_update.py` 为仅使用标准库的独立升级入口，旧安装可下载单文件做过渡升级；原 `static/release_update.py` 只保留共用校验的导出入口。GitHub 固定一个提交并逐项校验 Git blob，R2 校验清单、ZIP 大小和 SHA-256；禁止一条路径绕过另一条路径的依赖检查。删除在线覆盖文件的旧升级入口。

新版升级先在 `cache/update-jobs/` 暂存，依赖变化时在 `cache/update-environments/` 建立独立环境，执行依赖检查并用随机本机端口实际启动暂存程序。统一启动器在停止自己创建的服务后，备份程序与结构化数据、替换文件、切换环境，确认真实服务版本就绪后提交事务；失败或启动超时恢复，进程意外退出则下次启动恢复未完成事务。运行中的写请求与后台任务会阻止升级，新写请求在升级期间被拒绝。界面只在启动验证后确认完成，不提前更改版本显示。

边界：不升级 Python 解释器本身；旧 Windows 内置解释器不支持 venv 时准备阶段停止，需安装支持 venv 的 Python 后再使用入口。依赖变化需要网络。用户媒体、密钥和工作流不进入更新包；恢复针对本轮程序与结构化数据，不声称支持任意未来破坏性媒体迁移或任意历史版本降级。恢复点与旧环境保留，不自动清理。旧更新器仍不能凭空获得新能力，因此 2026.09.10 首次升级明确走单文件入口，以后使用新版启动器在线升级。
